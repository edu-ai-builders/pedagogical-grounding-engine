# 第2层：Context KG — 场景约束图谱

## 层定位

> **目标**：把"这个产品要在什么情境下解决什么问题"转化为结构化的约束节点。
> **产物**：10-15条 Context KG 三元组，每条附优先级和可牺牲性标注。
> **约束**：本层输出不允许引用论文内容，纯粹来自场景描述。

---

## 输入契约（Preconditions）

| 输入项 | 要求 | 缺失时处理 |
|---|---|---|
| 第1层 Core KG | 已完成 | 不允许跳过第1层直接执行第2层 |
| 场景描述 | 用户提供（任意格式）| 使用六维度模板主动追问 |

---

## 处理流程

### 阶段1：场景输入接收与结构化

**双轨输入处理**：

**轨道A：用户自由描述**
用户说任何关于场景的内容 → 模型自动映射到六维度 → 对缺失维度主动追问。

映射原则：
- 找到用户描述中对应六维度的内容，直接归类
- 不要强行解读；如果某段话可以归入多个维度，选最主要的那个
- 追问要简洁，一次性问所有缺失维度，不要一个个问

**轨道B：用户直接填模板**
直接进入阶段2，无需追问。

**六维度模板**：
```
目标用户：（谁在用？年龄段/角色/技术水平/学习背景/痛点描述）
学习情境：（课堂/在线同步/在线异步/混合/研讨班/自学/工作场景）
核心痛点：（现在最大的问题是什么？不用这个产品时会发生什么？）
成功标准：（什么行为/结果说明这个产品有效？要具体，不要"提升学习效果"）
约束条件：（技术限制/时间约束/资源/平台要求/语言/合规要求）
已有设计假设：（如果用户已经有了某些功能/设计想法，在这里列出）
```

**追问示例**（所有缺失维度一次性提问）：
```
我看到你描述了目标用户和核心痛点。在我开始之前，还需要了解：
- 成功标准：什么具体行为/结果说明产品有效？
- 约束条件：有技术限制吗（平台、语言、是否需要数据库等）？
- 学习情境：在线同步、异步还是线下？
可以一起回答，不用格式化。
```

---

### 阶段2：六维度完整性检查

**硬性要求**：六维度必须全部有内容，否则不进入阶段3。

| 维度 | 最低要求 | 完整性判断 |
|---|---|---|
| 目标用户 | 至少描述角色+一个关键特征 | "学生"不够，"大学生，阅读能力强但不愿口头发言"才够 |
| 学习情境 | 至少指明同步/异步 | — |
| 核心痛点 | 至少一个具体问题 | "学习效果不好"不够，"沉默学生无法暴露理解水平"才够 |
| 成功标准 | 至少一个可观察行为 | — |
| 约束条件 | 至少技术层面 | 如果用户真的没有限制，明确记录"用户无技术约束" |
| 已有假设 | 可以为空（明确记录"用户无已有假设"）| — |

---

### 阶段3：三元组提取

**格式**：
```
编号. **[主体]** → 谓词 → **[客体]** [维度标注] [H/M/L] [Must/Tradeoff/Nice]
```

**维度标注**（对应六维度）：`[用户]` `[情境]` `[痛点]` `[成功]` `[约束]` `[假设]`

**优先级标注（H/M/L）**：
- H（High）：直接关系到产品能否成立
- M（Medium）：重要但有变通方案
- L（Low）：锦上添花，不影响核心价值

**可牺牲性标注（Must/Tradeoff/Nice）**：
- Must：这个约束不可违反，否则产品失去意义
- Tradeoff：可以部分牺牲，但有代价
- Nice：理想情况下满足，但可以放弃

**⚠️ 关键原则**：优先级和可牺牲性是**独立维度**，不要简单等同。
- 例：`[H][Tradeoff]` = 很重要，但可以通过设计手段降级
- 例：`[L][Must]` = 不那么重要，但不能违反（如合规要求）

**数量指引**：10-15条。少于10条说明场景描述不够充分，重新追问。

**边界条件**：
- 不允许引用论文内容（这是第3层的工作）
- 不允许已有产品决策混入（用户说"我想要一个聊天界面"→ 归入[假设]，不作为约束）
- 技术约束（如"无数据库"）是真实约束，必须提取，不要因为"太技术性"而忽略

---

### 阶段4：约束冲突预判（轻量版）

在输出之前，快速扫描一遍所有约束节点，识别**明显的内部冲突**：

```
场景内部冲突检测：
- 某个[Must]约束是否与另一个[Must]约束在逻辑上矛盾？
- 如果有 → 在约束节点列表末尾标注：
  "⚠️ 内部冲突预警：[节点A] 与 [节点B] 可能存在张力，留给第3层详细处理"
```

这不是完整的冲突分析（第3层做），只是标记出显而易见的问题。

---

## 输出契约（Postconditions）

| 输出项 | 格式 | 保证 |
|---|---|---|
| 场景摘要 | 1-2句话 | 准确反映六维度核心内容 |
| Context KG 三元组 | Markdown 编号列表 | 10-15条，每条有三个标注 |
| 内部冲突预警 | 末尾标注（如有）| — |

**✅ 完成行格式**：
```
✅ 第2层完成：Context KG N条（用户X/情境X/痛点X/成功X/约束X/假设X）
              优先级分布：H=N, M=N, L=N；Must=N, Tradeoff=N, Nice=N
              [如有] ⚠️ 内部冲突预警N个
```

---

## 错误处理

| 错误情况 | 处理 |
|---|---|
| 用户只说"做一个教育app" | 使用追问模板，一次性问所有六维度 |
| 成功标准过于模糊（"提升学习效果"）| 追问："能描述一个具体的场景吗？比如学生做了什么，老师看到了什么？" |
| 用户的约束条件非常复杂（如企业级合规）| 提取核心约束，对复杂合规注明`[合规约束: 需要专业法律核实，此处仅作标记]` |
| 六维度信息矛盾（如用户说"线下课堂"又说"无需实时同步"）| 主动指出矛盾，要求澄清 |

---

## 质量自检

- [ ] 六维度是否全部覆盖？
- [ ] 每条约束是否有 H/M/L + Must/Tradeoff/Nice 两个标注？
- [ ] 是否混入了论文内容？（如有，移除）
- [ ] 是否混入了产品决策？（如有，移至[假设]维度）
- [ ] 完成行的分布数字是否准确？
