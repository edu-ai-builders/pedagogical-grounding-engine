# 第1层：Core KG — 论文本体知识图谱

## 层定位

> **目标**：把论文里的"什么是真的"提取出来，与场景无关，可复用。
> **产物**：每篇论文一个 Core KG，多篇时额外产出合并 KG。
> **约束**：本层输出不允许出现任何场景判断或产品设计推断。

---

## 输入契约（Preconditions）

执行本层前，以下内容必须已就绪：

| 输入项 | 要求 | 缺失时的处理 |
|---|---|---|
| 论文全文或摘要+方法+结论 | 至少包含方法论部分 | 主动要求用户补充 |
| 论文数量 | 1篇以上 | — |
| 合并模式 | 默认模式3，可由用户在启动时指定 | 未指定则静默使用模式3 |

---

## 处理流程（逐篇执行）

### 阶段1：论文类型判断（Gate Check）

这是一个硬性门控，在提取任何三元组之前执行。

```
读取论文 → 判断研究类型
    │
    ├── 元分析 / 综述 / 系统性文献回顾
    │   └── 停止该篇处理
    │       输出："[论文X] 为综述类型，适合作为文献基础而非直接实现来源。
    │              建议与方法论类论文配合使用。跳过，继续处理其他篇。"
    │
    ├── 方法论 / 实验+原型 / 技术方案+演示
    │   └── 继续执行阶段2
    │
    └── 类型不明确
        └── 主动询问："这篇论文是提出新方法/做实验/还是综述已有研究？"
            等待用户回答后继续
```

**已知误判风险**：部分论文同时包含文献综述章节（Related Work）和实验章节——判断依据是**整篇论文的主要贡献**，而非某个章节的存在。

---

### 阶段2：元数据提取

输出一张精简表，5行以内：

```
| 字段         | 内容                                    |
|------------|---------------------------------------|
| 标题         | [完整标题]                               |
| 研究类型       | [方法论 / 实验+原型 / 技术方案]                  |
| 核心贡献       | [1句话：这篇论文提出了什么？解决了什么问题？]             |
| 目标人群       | [研究对象是谁]                              |
| 核心系统/框架    | [如有，描述论文构建的系统/框架的名称和主要组件]            |
```

---

### 阶段3：核心构念识别

在提取三元组之前，先列出 5-8 个**核心构念**（名词）。

**识别原则**：
- 构念必须是论文中有明确定义或操作化描述的概念
- 不是泛化概念（如"学习"、"学生"），而是论文特有的概念（如"对话理解模块"、"参与度监控周期"）
- 如果同一构念在论文中有多个名称，统一为一个，标注别名

**输出格式**：
```
核心构念（N个）：
1. [构念名称] — [1句话定义]
2. ...
```

---

### 阶段4：三元组提取

**格式**：`编号. **主体** → 谓词 → **客体** [来源标注] [类型标注]`

**谓词**：必须来自 `references/kg-vocabulary.md` 的词汇表。如果词汇表中没有合适的谓词，可以新创建，但必须在三元组后面注明 `[自定义谓词: 含义]`。

**类型标注**（三选一）：
- `[陈述]`：描述"是什么"的构念关系
- `[程序]`：描述"怎么运作"的过程关系
- `[F]`：直接暗示一个可实现的产品功能（product-implied）

**数量要求**：
- 每篇：总计≥20条
- 陈述性≥7 / 程序性≥8 / [F]标注≥5
- 如果某个集群（如参与度检测、脚手架写作）特别密集，深挖到15条以上

**边界条件**：
- 不允许出现"应该"、"建议"、"可以考虑"——这是陈述事实，不是建议
- 不允许把场景信息混入 Core KG（如"在我们的app中"）
- 如果论文数据不足以支持20条，先输出所能提取的，在完成行注明"[数据不足: 仅能提取X条，原因：...]"

---

### 阶段4b：Representation Translation（表征跨语境迁移）

> **这不是 enrichment（填更多字段），而是 translation and transformation——**
> **把研究语境的表征，迁移到执行语境，成为设计决策的语言。**

#### 两个语境是两个不同的世界

**研究语境**：回答"这个现象存在吗？它在什么条件下成立？"
- 语言：因果关系、相关性、统计显著性
- 受众：同领域研究者
- 表征目的：证明和说服

**执行语境**：回答"我们应该做什么？做了之后会发生什么？"
- 语言：可操作约束、触发条件、失败模式、可观察指标
- 受众：设计者、工程师、教育者
- 表征目的：驱动决策和行动

这两个世界之间存在**语境张力（translation tension）**——
同一个概念在两个语境里可能需要用完全不同的词来命名，
表达的关系可能需要被重新结构化，而不只是翻译。

#### 迁移前的必问三个问题

在对任何 triple 做迁移之前，先问：

```
Q1：这条 triple 是在研究语境里"描述世界"，
    还是已经在暗示"如何改变世界"？
    → 后者可以直接迁移；前者需要先判断它是否值得迁移

Q2：这条 triple 的核心机制，
    在执行语境里是否仍然成立，还是需要被限定条件？
    → 研究结论往往有实验室边界条件，落地时这些条件可能不满足

Q3：这条 triple 被迁移之后，
    谁会用它来做什么决策？
    → 没有明确下游用途的迁移是无效迁移
```

#### 需要迁移的 triple 类型

**必须迁移**：
- 所有标注 `[F]`（product-implied）的 triple
- 所有标注 `[程序]` 的核心机制 triple
- 有 `[冲突]` 标注的 triple（需给出两种迁移路径）

**可以跳过**：
- 纯背景性 `[陈述]` triple（如"PBL 起源于医学教育"）
- 仅用于定位研究贡献的 triple（如"本研究填补了X领域的空白"）

#### Translated Triple Schema

每条需要迁移的 triple，输出以下结构：

```markdown
**[编号] 原始表征（研究语境）**
[主体] → [谓词] → [客体] [类型]

**迁移后表征（执行语境）**
[重新命名/重新结构化后的表达——如果原始语言已经可用，保持不变；
 如果研究语言无法直接驱动设计，在这里重写]

**translation_tension**（迁移张力）
→ 原始表征在研究语境中的边界条件是什么
→ 这些条件在执行语境中是否仍然成立
→ 如果不成立，迁移时做了什么假设或妥协

**cognitive_mechanism**
→ 这个关系通过什么认知/学习机制起作用（必须命名具体机制，见词汇表）

**activation_condition**
→ 这个机制在执行语境里需要什么前提才能被激活
→ 什么场景下它不会被激活（边界条件）

**failure_signature**
→ 当这个机制在产品/系统里失效时，会出现什么可观察的信号
→ 失效通常从哪里开始（不是"用户不喜欢"，而是机制层面的断裂点）

**execution_form**
→ 在产品/系统里，这条迁移后的 triple 最自然地对应什么执行形态
→ 从词汇表选择：ui_feature / prompt_rule / workflow_step / constraint / metric / graph_schema
→ 如果无法归入以上任何一类，说明迁移未完成，需要继续转化
```

#### 迁移质量标准

**translation_tension 必须是真实的张力**，不是空白字段：
- 合格：`研究在课堂环境下测试，但执行语境是异步在线学习——时间连续性假设不成立`
- 不合格：`迁移顺利，无明显张力`（几乎不存在零张力的迁移）

**cognitive_mechanism 必须命名具体机制**（从 kg-vocabulary.md 选择）：
- 合格：`元认知监控 / 检索练习 / 认知冲突 / 脚手架逐步撤除`
- 不合格：`帮助学习者更好地理解` / `促进学习`

**failure_signature 必须是机制层面的断裂**：
- 合格：`用户跳过自评步骤直接寻求外部验证，导致元认知监控回路断裂`
- 不合格：`用户不使用这个功能` / `用户觉得太复杂`

**execution_form 必须可以直接被下游层消费**：
- 如果选择了 `ui_feature`，第3层应该能直接把它作为 Context KG 对齐的候选
- 如果选择了 `prompt_rule`，第5层的 `/prompt` 命令应该能直接引用它
- 无法被下游消费的 execution_form = 迁移未完成

#### 冲突 triple 的特殊处理

当 triple 有 `[冲突: A主张X, B主张Y]` 标注时：

```markdown
**[编号] 冲突迁移**

迁移路径A（来自论文A）：
[按完整 schema 输出]

迁移路径B（来自论文B）：
[按完整 schema 输出]

迁移路径选择建议：
→ 两条路径在 execution_form 上有何差异
→ 场景偏向（如：路径A更适合异步/B更适合同步场景）
→ 不做裁决，把选择权交给第3层的 Constraint Layer
```

#### 输出格式

```markdown
## Translated Core KG — [论文简称]

### 已迁移的 triple（N条）

[按 schema 逐条输出，包含完整的 translation_tension 分析]

### 保持原始形态的背景性 triple（M条）

[仅列编号和原始 triple]

### 迁移摘要
- 迁移了 N 条 triple，识别出 K 条冲突需双路径处理
- 主要 cognitive_mechanism：[列表，来自所有迁移 triple 的汇总]
- 主要 translation_tension 类型：[研究边界条件 / 时间约束 / 样本特征 / 技术限制...]
- 执行形态分布：ui_feature×N / prompt_rule×M / ...
- 关键 failure_signature 模式：[1-2句话，指出最容易断裂的地方]
```

### 阶段5：多篇合并（仅多篇时执行）

**合并顺序**：先两两比较，识别同义和冲突，再合并。

**同义判断规则**（严格，避免过度合并）：
- 两个构念必须在操作层面完全等价（不只是名字相似）
- 如果有疑问，保留两者，标注`[可能同义: 待确认]`，不强行合并

**冲突判断规则**：
- 两篇论文对同一现象有不同的因果主张
- 或对同一概念有不兼容的操作化定义
- **冲突是有价值的信息，不要消除**，标注：`[冲突: A论文主张X, B论文主张Y]`

**合并输出格式**：
```
## Core KG — 合并结果

### 互补节点（直接合并，N条）
[列表，每条标注来源]

### 同义节点（已合并，M组）
[原名A = 原名B → 统一为: 合并名称 [合并自A+B]]

### 冲突节点（保留双方，K组）
[冲突描述，双方主张，标注[冲突]]
```

## 输出契约（Postconditions）

本层完成后，下一层可以依赖以下内容：

| 输出项 | 格式 | 保证 |
|---|---|---|
| 每篇论文的 Core KG 三元组列表（原始） | Markdown 编号列表 | ≥20条/篇，类型标注完整 |
| Translated Triple（阶段4b） | Markdown schema 结构 | 所有 [F] 和核心 [程序] triple 已完成跨语境迁移 |
| translation_tension 分析 | 迁移摘要 | 每条迁移 triple 标注了研究→执行语境的边界条件变化 |
| 主要 cognitive_mechanism 列表 | 迁移摘要 | 来自所有迁移 triple 汇总，命名了具体认知机制 |
| 合并 KG（多篇时）| Markdown 分类列表 | 冲突节点保留，双路径迁移已输出 |
| 核心构念列表 | Markdown 列表 | 5-8个/篇，有1句话定义 |

**关键保证**：
- 第3层（Constraint Layer）直接消费 `activation_condition` 作为约束节点输入
- 第3层的设计张力识别使用 `failure_signature` 作为障碍检测线索
- 第4层的 PG Checklist PG2 直接引用 `cognitive_mechanism`，PG6 引用 `failure_signature`
- 第5层的 `/prompt` 命令直接从 `execution_form === prompt_rule` 的迁移 triple 中提取

**✅ 完成行格式**：
```
✅ 第1层完成：[论文A: N条三元组，已迁移M条（含K条冲突双路径）]
              主要认知机制：[列表]
              主要迁移张力类型：[列表]
              执行形态分布：ui_feature×N / prompt_rule×M / ...
```

## 错误处理

| 错误情况 | 处理方式 |
|---|---|
| 论文只有摘要，缺少方法细节 | 提取可得的三元组，标注`[数据不足]`，主动询问是否能提供更多内容 |
| 论文是中文/其他语言 | 构念名称保留原语言，三元组格式不变 |
| 多篇论文主题差异极大，几乎无法合并 | 分别输出独立 Core KG，在合并结果章节注明"两篇论文几乎无重叠构念，建议分别建立独立 Context KG" |
| 用户提供的是论文链接而非内容 | 如有搜索工具则尝试获取；否则告知需要复制粘贴内容 |
